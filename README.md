# pi-dotfiles

Portable user-level configuration, utilities, and skills for [Pi](https://pi.dev) and other agent harnesses (Claude Code, Codex), maintained for `twKrash` and applied with [chezmoi](https://www.chezmoi.io). Pi packages are referenced, not vendored.

## Install

```sh
brew install chezmoi                                   # or see chezmoi.io/install
chezmoi init git@github.com:twKrash/pi-dotfiles.git    # asks: harnesses on this machine, Pi subagent profile
chezmoi diff                                           # review
chezmoi apply                                          # asks before replacing any existing file
```

### First adoption on a machine with existing files

- The generated config sets `lessInteractive = true`: `chezmoi apply` asks (diff / overwrite / skip) before replacing any file chezmoi did not write itself, including symlinks such as a linked `~/.pi/agent/AGENTS.md`. Without a terminal it stops instead of overwriting.
- Before the first apply changes anything, a one-time script backs up every existing managed path to a fresh `~/.local/state/pi-dotfiles/adoption-backup-<timestamp>.<random>/` (mode 0700): `paths/` holds managed paths as they were (symlinks kept), `ancestors/` holds parents that are symlinks or plain files (chezmoi would replace them with directories), and `COMPLETE` marks a finished snapshot. A failed attempt leaves its partial snapshot without `COMPLETE`; the retry writes a new one.
- Moving from `setup.sh`: rules in `~/.config/pi-dotfiles/local.md` move to `~/.config/chezmoi/local.md`. Rendering stops with an explicit message while the old file exists; if both exist, merge the old rules into the new file and delete the old one.

`chezmoi init` writes `~/.config/chezmoi/chezmoi.toml` with `sourceDir` (this checkout), the selected `harnesses` (`pi`, `claude`, `codex`), the Pi subagent `provider` profile (`none`, `claude`, `codex`), and `nvim -d` as merge tool. Answers are remembered; run `chezmoi init` again after the config template (`home/.chezmoi.toml.tmpl`) changes. Requirements: chezmoi >= 2.72.0 (enforced by the config template), Node.js (already required by Pi), and `~/.local/bin` on `PATH`.

## Daily use

| Task | Command |
|---|---|
| Update | `git pull --ff-only && chezmoi diff && chezmoi apply` |
| A managed file was edited locally | `chezmoi apply` asks (diff / overwrite / skip); `chezmoi merge <file>` opens a 3-way merge |
| Copy a local edit back into the repo | `chezmoi re-add <file>` (plain files), then commit |
| Machine-only instructions | edit `~/.config/chezmoi/local.md` (all harnesses) or `local.<harness>.md` (one harness), then `chezmoi apply` |

## Harnesses

Each selected harness gets its own generated global instructions file; files of unselected harnesses are not installed (`home/.chezmoiignore`).

| Harness | Generated file | Contents |
|---|---|---|
| `pi` | `~/.pi/agent/AGENTS.md` | core + `instructions/harness-pi.md` + local + `local.pi.md` |
| `claude` | `~/.claude/CLAUDE.md` | core + `instructions/harness-claude.md` + local + `local.claude.md` |
| `codex` | `~/.codex/AGENTS.md` | core + Codex addendum + local + `local.codex.md` |

Core is `instructions/core.md` (no harness or provider specifics). Local is the optional `~/.config/chezmoi/local.md` for machine- or employer-specific rules; it never enters the repo. Rules for a single harness go in `~/.config/chezmoi/local.<harness>.md` (`local.pi.md`, `local.claude.md`, `local.codex.md`), appended after `local.md` for that harness only. Edit these sources, not the generated files. Pi config, `prompt-opt`, and the prompt lab are installed only when `pi` is selected. The Pi addendum lives inside `AGENTS.md` because Pi always loads the global `AGENTS.md`, whereas a trusted project's `.pi/APPEND_SYSTEM.md` replaces the global `APPEND_SYSTEM.md`. Source files avoid the names `AGENTS.md`/`CLAUDE.md` so agents working in this repo do not load them as context. Target paths are fixed (`~/.pi/agent`, `~/.claude`, `~/.codex`).

## Layout

`.chezmoiroot` points chezmoi at `home/`, which mirrors `~` using chezmoi's [source naming](https://www.chezmoi.io/reference/source-state-attributes/) (`dot_` → `.`, `private_` → mode 0700/0600, `executable_`, `create_`, `empty_`, `modify_`, `.tmpl`). `~/.pi/agent` and its `extensions/` stay private because they sit next to Pi credentials. Plain files are copied as-is (and support `chezmoi re-add`); only generated files are templates.

- `home/dot_local/bin/executable_prompt-opt`, `prompt-opt-history.mjs`: the prompt optimizer CLI (`~/.local/bin`).
- `home/ai/prompt_engineering/`: canonical prompt-engineering lab (`~/ai/prompt_engineering`, the `prompt-opt` default; `PROMPT_LAB_DIR` overrides at runtime).
- `home/dot_pi/private_agent/private_extensions/`: prompt-opt Pi adapter plus permission-system merge, RTK optimizer, and subagent settings.
- `home/dot_pi/private_agent/skills/prompt-engineering/`: Pi skill generated from the lab (`SKILL.md` = Pi metadata + lab `AGENTS.md`; references included from the lab).
- `instructions/code-standards.md`, `home/.chezmoitemplates/code-standards-skill.tmpl`: the `code-standards` skill (design, Python, testing, quality-gate and module-size rules), installed as `SKILL.md` under `~/.pi/agent/skills/code-standards/`, `~/.claude/skills/code-standards/` and `~/.codex/skills/code-standards/` for the selected harnesses. Core only points to it, so the rules load on demand instead of in every session. A guard enforces the load: the first write or edit of a Python or TypeScript file (`.py`, `.pyi`, `.ts`, `.tsx`, `.mts`, `.cts`) in a session is blocked while the skill is not in the model's context: it is read once per session and again only after compaction drops it (Claude Code re-attaches skills loaded through the Skill tool, so those survive compaction). In Pi that is `home/dot_pi/private_agent/private_extensions/code-standards-guard.js` (`~/.pi/agent/extensions/`, also loaded into every subagent through `subagents.defaultSubagentOnlyExtensions`). In Claude Code it is `home/dot_claude/hooks/executable_code-standards-guard.mjs`, a `PreToolUse` hook that checks the session or subagent transcript. The `worker` and `reviewer` subagents list the skill too; the merge adds the guard extension and these skill entries to existing local lists.
- `home/dot_local/bin/executable_code-gates`, `home/dot_pi/private_agent/private_extensions/code-gates.js`, `home/dot_claude/hooks/executable_code-gates-hook.mjs`: the code-standards quality gates ([crapper](https://github.com/unclebob/crapper), [dryer](https://github.com/unclebob/dryer), [mutator](https://github.com/unclebob/mutator), installed with `uv tool install`). `code-gates quick <file>` runs after each Python or TypeScript edit and appends functions with complexity 10 or above and duplicates of that file to the tool result; dryer gets the files git tracks or would track, and the metrics go to `~/.cache/code-gates`, so the repository is untouched. The commit gate is a global git `pre-commit` hook (config-based hooks, git 2.54+; it runs next to repository hooks, including `core.hooksPath` ones): `code-gates check` fails an agent's commit (`PI_CODING_AGENT` or `CLAUDECODE` set) of code files until `code-gates run` (dryer, crapper with coverage, mutator; `--no-mutator`, `--test-command`, `--coverage-command`) has run on exactly the tree being committed. git hands the hook the index the commit records, so `commit -a`, `commit <paths>` and any way of staging are covered without reading the command. Your own commits are not gated; `CODE_GATES_SKIP=1` skips the gate. Nothing here writes git config: `code-gates doctor` prints the commands for missing tools, the hook and the `.metrics/`/`target/` lines in the global ignore file git reads, sessions start with that notice, and the code-standards skill tells agents to run the commands only after you approve. Repo Claude hooks are matched by matcher and command, so a local group running the same command under another matcher does not suppress them. Pi loads the extension in the main session and every subagent; Claude Code gets `PostToolUse` and `SessionStart` hooks. Everything fails open when `code-gates` or a tool is missing.
- `home/dot_config/private_ai-memory/create_empty_MEMORY.md`: shared memory template (`~/.config/ai-memory/MEMORY.md`, used by every harness), created only when absent (an existing file, even an empty one, is kept). An old `~/.pi/agent/MEMORY.md` with real content stops `chezmoi apply` until it is merged into the shared file and deleted; the untouched template stub or a blank file does not block.
- `home/dot_local/bin/executable_ai-mem`, `home/dot_config/private_ai-memory/create_structure.json`: `ai-mem` (Python 3, standard library only) reads and appends static metadata caches (JSONL, newest line per key wins, per-file TTL marks `_stale` records). Which caches exist is machine-local: `~/.config/ai-memory/structure.json` maps each source to its directory, schema doc, purpose and TTLs, and is created empty once, never overwritten. Example: `{"sources": {"atlassian": {"dir": "~/work/memory/atlassian", "doc": "~/work/memory/README.md", "purpose": "Jira/Confluence IDs", "ttl": {"jira/teams": 30}, "defaultTtl": 90}}}`. `ai-mem sources` lists them; `ai-mem get atlassian/jira/teams <key>` reads `<dir>/jira/teams.jsonl`. A miss exits 1; anything else that goes wrong exits 2 (bad input, unknown sources, paths outside a source, and manifests or cache files that are malformed, unreadable or not UTF-8), so a broken cache never reads as a miss. Cache lines that are not a JSON object with a string `k` are skipped with a note; a `ts` that is missing, malformed, timezone-less or in the future counts as stale. Manifest `dir` must be absolute (after `~`), and TTLs are whole days from 1 to 36500. Usage rules are in `ai-mem --help`. Write approval per source belongs in local rules, not the manifest.
- `home/dot_pi/private_agent/modify_settings.json.tmpl`, `modify_mcp.json.tmpl`: merge repo defaults into the live files via `scripts/merge-json.mjs` (stdin → stdout). Unrelated settings, extra packages, other MCP servers, and keys Pi writes itself are kept; conflicting local values win and are reported. The `claude`/`codex` profile replaces only subagent model/thinking fields; `none` leaves models untouched. The Claude profile adds `npm:pi-claude-agent-sdk` (packages are not installed; use `pi update --extensions` after review).
- `home/.chezmoitemplates/instructions.tmpl`: composes the per-harness instruction files.
- `instructions/`: core and per-harness instruction sources.
- `agent/settings.json`, `agent/mcp.json`, `agent/providers/`: merge inputs (package list and portable `pi-subagents` role defaults; Context7 only, no personal MCP headers; opt-in `codex` and `claude` subagent profiles).
- `claude/settings.json`, `home/dot_claude/modify_private_settings.json.tmpl`, `home/dot_claude/executable_statusline.sh`: Claude Code plugins (`extraKnownMarketplaces`, `enabledPlugins`) and the status line. Defaults are merged into `~/.claude/settings.json` by `scripts/merge-json.mjs claude`: missing keys are added, local values win and are reported, permissions are never touched, and repo hooks (the code-standards guard) are added once next to local hooks, which are never changed. The exception is `autoMemoryEnabled: false`, which is enforced because core instructions forbid harness auto-memory. Plugins are not installed by the merge (run `claude plugin install <name>@<marketplace>` or let Claude Code offer them) and run code, so review them before installing. `claude/mcp.json` lists the user-scope MCP servers (Context7, GitHub); `home/run_onchange_after_20-claude-mcp.sh.tmpl` runs `scripts/claude-mcp-sync.mjs`, which registers missing servers through `claude mcp add-json --scope user` and leaves existing ones alone (it skips when the `claude` CLI is absent, and reruns once `claude` is on `PATH` because the script embeds its path; it never edits `~/.claude.json` directly). The GitHub server fetches its token from `gh auth token` at connect time, so no secret is stored. Add a plugin by listing it in `claude/settings.json`; the Claude addendum tells the agent to do that when asked to install one.
- Graphify skill: not vendored. Install it with `graphify install --platform pi` (and `--platform claude`) and re-run after upgrading graphify.
- `tests/`: `sh tests/prompt-opt.sh`, `sh tests/ai-mem.sh` `node tests/code-standards-guard.mjs`, `node tests/code-gates.mjs` and `sh tests/chezmoi.sh` (applies into throwaway homes; never touches `~`).

### Prompt optimizer

`prompt-opt --model=sol` now selects GPT-6.1 Sol (`gpt-6.1-sol`). Use `--model=sol-6` for GPT-6 Sol (`gpt-6-sol`) or `--model=sol-6.1` explicitly for GPT-6.1 Sol.

Add `--goal` to `/prompt-opt` to run Goal mode: the optimizer returns the complete optimized task plus a Definition of Done and a stop condition. A task that fits pi-goal's 4,000-character limit is activated inline with no file; a longer one is persisted as an immutable handoff under `~/.pi/agent/handoffs/<session-id>/`. Before anything starts, the extension previews the handoff location as its first line (or `not needed` for an inline task), then the Goal objective, and requires `proceed`, `edit`, or `cancel`; `edit` reopens the complete authoritative task (the handoff file for long tasks) and re-optimizes it. If the request does not define concrete acceptance criteria, the extension asks a clarifying question before previewing. Goal mode never writes the prompt editor. The flag requires `rpc.enabled` in `~/.pi/agent/pi-goal.json`, which this repo enables while keeping other settings. Run `prompt-opt` for interactive prompt editing or pass a task file/stdin. Use `/prompt-opt` inside Pi to insert optimized output into the editor; `/prompt-opt --help` displays CLI usage in a TUI notification without replacing the editor contents, and argument completion suggests documented options and known values. Use `prompt-opt --history` to list recorded request hashes and `prompt-opt --history HASH` (or `/prompt-opt --history=HASH`) to display original and optimized prompts. `--no-cache` forces another run while preserving prior records. Cache identity includes the exact request bytes, seven resolved settings, prompt-lab files, Pi version, and contract revision. The optimizer run loads only the lab `AGENTS.md` (`--no-context-files`), so global or ancestor `AGENTS.md`/`CLAUDE.md` files do not affect results. Legacy results remain visible as unverified. Add `--debug` (alias `--verbose`) to log phase timings; the extension records metadata-only `prompt-opt-debug` entries in the current session. Run `prompt-opt --help` for options. If your Pi serves Anthropic models through another provider, set `PROMPT_OPT_ANTHROPIC_PROVIDER` (for example `claude-bridge`); `PROMPT_OPT_RUNNER_EXTENSION` loads that provider's extension file for the optimizer run (all other extensions stay disabled). The command needs `~/.local/bin` on `PATH`; clipboard copy uses `xclip` when available, otherwise `pbcopy`.

Provider profiles set scout to a low-cost model, worker to a mid-tier model, reviewer to Opus 5.5 at medium effort, and oracle to Opus 5.5 at high effort for Claude. Use per-run thinking overrides for oracle `xhigh` when task warrants it. No provider option leaves existing models untouched.

The package list follows the currently selected npm/Git extensions. `pi-session-inspector` uses its published package (`@twkrash/pi-session-inspector@1.5.3`), not a development checkout. Pi packages can execute code; review them before installing.

The permission defaults (`agent/permission-system.json`) follow `@gotgenes/pi-permission-system`'s config format and are installed in full only when `~/.pi/agent/extensions/pi-permission-system/config.json` does not exist yet. An existing file, even a blank one, is only ever tightened (`scripts/merge-json.mjs permission`), judged by the plugin's rules (last matching rule wins within a surface; a surface without its own `*` falls back to `permission["*"]`, which defaults to `ask`; `path`/`external_directory` rules run before their `_read`/`_write` rules): a missing repo `deny`/`ask` rule is appended only if it is stricter than what that surface decides by default, and an `ask` is never added where a local `deny`, including the `{"action": "deny", "reason": …}` form, could match first. Repo `allow` rules, top-level `mcp__*` keys (the plugin copies their rules after every `mcp` rule), a local surface written as a single string, keys outside `permission` (such as the log settings) and every local value are left alone. The guarantee covers this global file only: an agent or project config that is stricter than this file, through its own `"*"` or a surface map, can be overridden by a rule later appended here, so such a config should set each surface it restricts as a single string (`"bash": "deny"`). A rule you delete locally can come back; allow rules added to the repo reach existing machines only by hand, and rules removed from the repo stay on machines that already have them. The live file must be plain JSON: the plugin accepts `//` and `/* */` comments, but the merge stops `chezmoi apply` on them rather than drop them. It keeps the plugin's allow-within-project default, denies secret-like `.env` files, asks before destructive shell commands (`rm -rf`, `sudo`, `git push`, `git reset --hard`, `git clean`) and external-directory access, and grants only explicit global tool paths. Reads and writes use separate external-directory rules. Machine-specific paths (code checkouts, user home paths) belong in the live file, never in the repo defaults. Debug and review logs are enabled on a fresh install so `permission-review` decisions can be audited (existing files keep their own settings); they retain prompts and tool inputs on disk, so set `debugLog`/`permissionReviewLog` to `false` locally if that is unwanted.

## Repository protection

`main` is protected: changes require a pull request; force pushes and branch deletion are disabled; administrators are subject to the rule. No approval count is required so a sole maintainer can merge their own PR. Public users can submit PRs but have no direct write access. Only maintainers with repository write permission can merge.
